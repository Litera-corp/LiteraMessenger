### Данный документ описывает правила работы с Git и GitHub в нашей команде, чтобы обеспечить единый стиль, порядок и удобство командной разработки.

---

## 1. Основная стратегия ветвления

Мы используем упрощённую стратегию **Git Flow**:

- **main** — стабильная ветка с релизами (продакшен).
- **dev** — основная ветка разработки. Сюда вливаются все фичи после _**code review**_.
- **feature/** — ветки для разработки новых функций.
- **bugfix/** — ветки для исправления багов в `dev`.
- **hotfix/** — ветки для срочных исправлений в `main`.
- **release/** — ветки подготовки релизов.

---

## 2. Правила именования веток

Используем формат:

`task-<id-задачи>`

Примеры:
- `task-12`
- `release/1.0.0`

---

## 3. Коммиты

### Формат сообщений коммитов:

`<тип>: <краткое описание>`

#### Основные типы:
- `feat:` — новая функциональность  
- `fix:` — исправление бага  
- `docs:` — изменения в документации  
- `style:` — форматирование (не влияющее на код)  
- `refactor:` — рефакторинг без изменения функционала  
- `test:` — добавление или изменение тестов  
- `chore:` — рутинные задачи (обновления зависимостей и т.п.)

#### Примеры:
- `feat: добавлен экран регистрации`
- `fix: исправлен баг с отправкой сообщений`
- `refactor: вынесена логика авторизации в сервис`

> ✅ Описание к задаче писать в **обезличенной** форме.

---

## 4. Pull Request (PR)

1. Перед созданием **PR**:
   - Обновите свою ветку (`git pull origin dev`).
   - Убедитесь, что код компилируется и проходит тесты.
2. Создание **PR**:
   - **PR** всегда направляется в `dev`.
   - Название **PR** должно совпадать с названием задачи.
   - В описании **PR** укажите:
     - Что было сделано.
     - Как проверить.
     - Ссылку на задачу/issue.
3. Минимум **1 ревью от другого участника** перед merge.

---

## 5. Code Style

- Соблюдаем единый стиль кода (настройки линтера/formatter — обязательны).
- Не коммитим временные файлы (`.idea`, `.vscode`, `node_modules`, `vendor` и пр.) — всё должно быть в `.gitignore`.
- Каждый PR должен быть маленьким и решать одну задачу.

---

## 6. Рабочий процесс

1. Берём задачу из трекера
2. Создаём ветку от `dev`:
```bash
git checkout dev
git pull
git checkout -b task-12
```
3. Делаем коммиты по правилам.
4. Отправляем ветку на GitHub:
```bash
git push -u origin task-12
```
5. Создаём PR → ждём ревью → после одобрения вливаем в `dev`.
6. После завершения релиза `dev` вливается в `main`.

> При создании Pull Request-а в описание всегда указывать описание задачи из YouGile-а

---

## 7. Подсказки

- 1 задача = 1 **PR**.
- Часто пушьте свои изменения, чтобы не потерять наработки.
- Перед merge обязательно **решайте конфликты локально**.
- Если ветка неактуальна — удаляйте её после merge.
- Ведите обсуждение в **PR**, а не в чате — чтобы сохранялась история.
